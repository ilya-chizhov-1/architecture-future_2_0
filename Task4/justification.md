# Обоснование конфигурации Terraform

Terraform разворачивает на Yandex Cloud учебную трёхзвенную инфраструктуру (bastion + app + db) в одной зоне `ru-central1-a`. Ниже - выбор ресурсов и параметров, логика IaC, шаги запуска и проверки.

## Сеть

- **VPC с двумя подсетями (public, private)** - классическая схема изоляции. Bastion в публичной подсети - единственная точка входа по SSH, app и db в приватной без публичных IP: уменьшаем атакуемую поверхность.
- **CIDR /24** для каждой подсети (`10.10.1.0/24`, `10.10.2.0/24`). Хватает на сотни адресов, при этом диапазоны непересекающиеся и легко читаются.
- **NAT-gateway** через `yandex_vpc_gateway` с `shared_egress_gateway {}` плюс `yandex_vpc_route_table` с маршрутом `0.0.0.0/0` в шлюз. Даёт приватным ВМ исходящий доступ (обновления пакетов, вызовы внешних API), не открывая их снаружи. Используется управляемый NAT-шлюз вместо NAT-инстанса: не нужно поддерживать отдельную ВМ и её отказоустойчивость.

## Группы безопасности

- **Раздельные SG на роль** (sg_bastion, sg_app, sg_db). Это позволяет описывать правила ссылками на другие SG, а не на CIDR - если меняется IP, правила остаются корректными.
- **sg_bastion**: SSH (TCP 22) только из `admin_cidr`. В `terraform.tfvars` по умолчанию стоит `0.0.0.0/0` для удобства проверки, на проде заменяется на `<ваш-ip>/32`.
- **sg_app**: SSH только из sg_bastion, HTTP (80) из публичной подсети. Без доступа с улицы.
- **sg_db**: Postgres (5432) только из sg_app, SSH только из sg_bastion. Изолируем БД от прямого доступа любым клиентам кроме приложения.

## Виртуальные машины

- **Ubuntu 22.04 LTS** (`image_family = "ubuntu-2204-lts"`) - актуальная LTS с поддержкой до 2027.
- **Bastion**: 2 vCPU / 2 GB - достаточно для SSH-прокси и мелких утилит, дороже не нужно.
- **App / DB**: 2 vCPU / 4 GB - учебный минимум под веб-приложение и Postgres. В реальном продакшене размер подбирают по профилю нагрузки; здесь параметризовано через `variables.tf`, легко поменять.
- **platform_id = "standard-v3"** - актуальное поколение Intel Ice Lake в Yandex Cloud, хорошее соотношение цена/производительность. Не `preemptible`: учебный запуск короткий, но bastion и db не должны падать в момент `terraform apply`.
- **allow_stopping_for_update = true** - разрешает Terraform перезапускать ВМ при изменении параметров (например, размера). Без него изменение `resources.cores` требует ручной остановки.

## Диски

- **Boot-диск 20 GB network-ssd** - Ubuntu + базовые пакеты укладываются в ~5 GB, остальное запас для логов и пакетов.
- **Data-диск 50 GB network-ssd** для db - отдельно от boot. Это даёт три плюса:
  1. Данные БД переживают пересоздание ВМ (диск остаётся).
  2. Легко снять снапшот и восстановить.
  3. Чёткое разделение: boot - stateless, data - stateful.
- Оба диска - `network-ssd`. `network-hdd` был бы дешевле, но медленнее и не подходит даже для учебного Postgres.

## Что управляется Terraform, а что вручную

**Terraform** (см. `main.tf`): VPC, обе подсети, route table, NAT-gateway, три SG, три ВМ (bastion, app, db) с их boot-дисками, отдельный data-диск у db.

**Вручную** (однократная подготовка, см. диаграмму):
1. Регистрация аккаунта Yandex Cloud и биллинг.
2. Cloud и Folder в консоли (их ID попадают в `terraform.tfvars`).
3. Сервисный аккаунт с ролями `editor` / `compute.admin` / `vpc.admin` и JSON-ключ - Terraform аутентифицируется через него.
4. SSH-ключ на рабочей станции (`ssh-keygen`). Публичная часть подставляется в `ssh_public_key`.
5. Установка Terraform CLI; `terraform init` скачает провайдер yandex-cloud/yandex.

Эти шаги не автоматизируются потому, что это bootstrap: создавать сервисный аккаунт в том же Terraform, от имени которого Terraform работает, - вопрос курицы и яйца. SSH-ключи и JSON-ключи - чувствительные секреты, которым не место в состоянии Terraform.

## Почему декларативный подход

- Описываем **целевое состояние**, а не пошаговые команды. Terraform сам выстраивает граф зависимостей и решает порядок операций. Не надо помнить, что VPC создаётся до подсетей, а SG - до ВМ.
- **Идемпотентность**: повторный `terraform apply` без изменений в коде ничего не делает. Нет риска дублей ресурсов от повторного запуска.
- **Видимый diff**: `terraform plan` показывает, что именно изменится, до внесения изменений. Это критично для ревью инфры в пулл-реквестах.
- **Drift detection**: если кто-то изменил ресурс руками в консоли, следующий `plan` покажет расхождение.

## Как IaC помогает воспроизводимости и масштабированию

- **Воспроизводимость**: один и тот же код + `terraform.tfvars` = одна и та же инфра, в любом folder, с любого рабочего места. Dev, staging и prod собираются из одного кода с разными `.tfvars`.
- **Версионирование в git**: история изменений инфры отслеживается так же, как код приложения; изменения проходят через PR и ревью.
- **Масштабирование**: чтобы поднять ещё один app-сервер, достаточно вынести `yandex_compute_instance.app` в `count = 2` или `for_each`. Аналогично - для нового окружения: `terraform workspace new staging` и новый `.tfvars`.
- **Disaster recovery**: если зона упала или ресурсы удалены, восстановление - `terraform apply` с тем же state. Без IaC - часы ручного кликанья в консоли.
- **Подключение нового бизнес-направления**: добавить новый модуль с той же структурой (VPC-subnet-VM-SG) - вопрос копирования и подстановки переменных.

## Как запустить и проверить

1. Заполнить `terraform.tfvars` реальными значениями (`cloud_id`, `folder_id`, `service_account_key_file`, `ssh_public_key`, `admin_cidr`).
2. Положить JSON-ключ сервисного аккаунта по пути, указанному в `service_account_key_file`.
3. Выполнить:
   ```bash
   terraform init
   terraform plan
   terraform apply
   ```
4. После успешного `apply` Terraform выведет значения из `outputs.tf`: публичный IP bastion, внутренние IP app и db, готовые команды для SSH.
5. Скриншот успешного `terraform apply` приложить к пулл-реквесту (требование задания).
6. Для уборки - `terraform destroy`.
