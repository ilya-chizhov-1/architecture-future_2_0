# Разделение системы на домены

## Состав доменов

Четыре бизнес-домена + один будущий домен партнёров + общая платформа данных как enabling-домен.

| # | Домен | Ответственность | Основные системы | Публикуемый data-продукт |
|---|-------|-----------------|------------------|---------------------------|
| 1.0 | Клиники | Приём пациентов, медицинские карты, истории болезни, назначения, снимки | Веб-клиент оператора, сервис клиник (API), база клинических данных, хранилище снимков | Операционные метрики клиник (поток пациентов, загрузка, выручка) без медицинских данных |
| 2.0 | Финтех | Платежи, счета, кредиты, банковские продукты, ПОД/ФТ | Финтех-сервисы (Go, Java), база финансовых транзакций | Агрегированные транзакции и продукты для аналитики |
| 3.0 | ИИ | Модели диагностики и рекомендаций, встраивание подсказок в работу врача | ИИ-сервисы (Python), реестр моделей | Метрики качества моделей, клинические исходы |
| 4.0 | Головной офис | HR, инвентаризация, корпоративные финансы, консолидация группы | ERP, HR-система, инвентарь, сервис консолидации | Ключевые показатели группы, консолидированная финансовая отчётность |
| 5.0 | Партнёры (перспективно) | Подключение новых бизнес-направлений: фарма, электроника | Системы партнёра + адаптер к контракту платформы | По контракту домена-партнёра |
| 6.0 | Платформа данных (enabling) | Приём данных, хранение, подготовка, витрина самообслуживания, governance | Шина событий и CDC, озеро данных, движок запросов, семантический слой, портал самообслуживания, BI, каталог данных, управление доступом | Аналитические витрины и бизнес-метрики для всех пользователей |

## Хранилища

| ID | Хранилище | Владелец | Что лежит | Кто читает |
|----|-----------|----------|-----------|------------|
| D1 | Озеро данных | Платформа данных | Data-продукты всех доменов в аналитическом виде | Платформа (для витрин), ИИ (для исторической аналитики) |
| D2 | Изолированная медицинская песочница | Клиники (владелец данных) + Платформа (технический оператор) | Медицинские данные под контрактом, только для обучения моделей | ИИ-домен с аудитом доступа. В общую витрину не попадает. |

## Логика разделения

- **Границы по бизнес-ценности.** Лечение, банковские услуги, модели ИИ и корпоративное управление - это разные бизнесы с разными метриками успеха, разными командами и разным темпом изменений. Каждый получает свой домен.
- **Владение данными на стороне домена.** Данные принадлежат тому домену, который их порождает. DWH перестаёт быть местом «общих» данных и централизованной логики.
- **Единый контракт между доменами.** Каждый домен публикует data-продукт в общем формате через платформу. Соседние домены не лезут в чужие базы напрямую.
- **PHI изолированы.** Медицинские данные никогда не выходят за контур домена Клиник. Исключение - изолированная песочница D2 для обучения моделей, с аудируемым контрактом.
- **Платформа данных - enabling-домен.** Она не несёт бизнес-логики, только предоставляет инструменты: приём, хранение, витрину, governance. Бизнес-логика возвращается в домены.
- **Новый бизнес = новый домен.** Партнёр-фарма или электроника подключаются по той же схеме, что и существующие домены: собственные системы + data-продукт по контракту. Никаких правок ядра.

## Преимущества для бизнеса

1. **Time-to-market.** Команда финтеха или ИИ выкатывает изменения в своём домене и не ждёт релизного окна DWH. Раньше любое изменение шло через одну центральную команду - теперь независимо.
2. **Независимое развитие направлений.** Финтех может экспериментировать с кредитными продуктами, ИИ - пробовать новые модели, а клиники - менять процессы приёма, не задевая друг друга.
3. **Уход от монолитного DWH.** Бизнес-логика и данные возвращаются в домены; старый DWH переводится в архивный режим и постепенно выводится из эксплуатации. Уходят EOL-риски SQL Server 2008 и блокировка на одной команде.
4. **Масштабирование на новые направления.** Подключение фармы или электроники становится проектом «новый домен + контракт», а не «правка DWH и ESB-маршрутов». Стоимость расширения экосистемы падает.
5. **Комплаенс по медицинским данным.** PHI не смешаны с корпоративной аналитикой; аудит упрощён, регуляторные риски снижены.
6. **Быстрая и единая отчётность.** Портал самообслуживания поверх семантического слоя даёт бизнесу готовые метрики по всем доменам без обращения к ИТ.

## Как бизнес-сценарии обеспечиваются потоками данных

Потоки см. в `data_flow.drawio` (уровень 1, нотация Gane-Sarson).

- **Интеграция нового финтех-сервиса.** Финтех (2.0) изменяется внутри: добавляется новый продукт и обновляется его data-продукт. Платформа (6.0) подхватывает изменение через шину событий и обновляет D1. Бизнес-пользователь сразу видит новые метрики в витрине. Ни DWH, ни другие домены не задеты.
- **ИИ анализирует медицинские данные.** Клиники (1.0) публикуют срез медицинских данных в D2 по контракту с аудитом. ИИ (3.0) забирает обучающую выборку из D2, обучает модели и возвращает подсказки обратно в клиники через API. PHI остаются в защищённом контуре: в D1 и витрину они не попадают.
- **Подключение нового партнёра (фарма или электроника).** Создаётся домен 5.0 с собственным data-продуктом. Он публикуется в Платформу (6.0) тем же механизмом, что у остальных доменов. В витрине появляется новая область без правки существующих доменов.
- **Быстрая отчётность самообслуживания.** Бизнес-пользователь через портал внутри 6.0 строит отчёт на семантическом слое, который обращается к D1. Данные собираются из data-продуктов всех доменов - ждать центральную команду не надо.
- **Аудит регулятора.** Регулятор обращается к Платформе данных (6.0) за отчётами и к каталогу/lineage, чтобы проверить происхождение цифр. D2 доступна отдельно с полным журналом обращений.
